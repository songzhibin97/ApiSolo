## 1. [高] createEnvironment() on an already-existing name silently blanks it, and the next save destroys the real environment file (including vault secrets)

- **位置**：`src/stores/environments.ts:144`　**维度**：前端/Store　**类别**：data-loss　**验证置信度**：high

**问题**：createEnvironment() never checks whether the name already exists; it adds the name to pendingEnvironmentNames and blanks variables, so a real saved environment is shown as empty and saveEnvironment() then overwrites its file with only the newly typed rows.

**失败场景**

Project `demo` has environment `dev` with `API_URL=https://dev` (plain) and `TOKEN=t` (secret, in the vault). The user opens EnvironmentPanel > New environment, types `dev` (a name that already exists — neither the panel nor the store rejects it) and confirms. Store state becomes activeEnv="dev", variables=[] and the panel shows an empty environment. The user adds `ONLY_NEW=1` and clicks Save. `saveEnvironment()` invokes `save_environment` with `{name:"dev", variables:[{key:"ONLY_NEW",...}]}`; src-tauri/src/lib.rs:1930 rewrites both `dev.env.json` and `dev.env.secrets.json` from that list, so `API_URL` and the secret `TOKEN` are permanently gone (the vault blob is orphaned with no index entry). Reproduced: after createEnvironment('dev') the store reported `variables = []` and the save payload was `{"name":"dev","variables":[{"key":"ONLY_NEW","value":"1","secret":false}]}`. A second route to the same corruption: pendingEnvironmentNames is never cleared on project switch, so drafting `staging` in project A and then switching to project B (which has a real `staging`) shows B/staging as empty for the same reason (loadEnvironment early-returns at environments.ts:73).

**证据**

```
function createEnvironment(name: string) {
  const normalized = normalizeName(name)
  ...
  if (!environments.value.includes(normalized)) {
    environments.value = [...environments.value, normalized].sort(...)
  }
  pendingEnvironmentNames.add(normalized)   // line 156 — added even when it already exists
  activeEnv.value = normalized
  variables.value = []                       // real env now displayed as empty
}
// and loadEnvironment(), line 73:
if (pendingEnvironmentNames.has(name)) { activeEnv.value = name; variables.value = []; return null }
```

**修复**

In createEnvironment(), reject (or switch to) a name that is already in environments.value instead of marking it pending: `if (environments.value.includes(normalized)) { throw new Error(t('errors.environmentAlreadyExists')) }` before the pendingEnvironmentNames.add. Additionally clear pendingEnvironmentNames in the projectsStore.activeProject watcher so drafts cannot leak into another project.

## 2. [高] $'...' ANSI-C quoting is not recognized, producing $-prefixed header names and literal escape sequences

- **位置**：`src/utils/curl-parser.ts:329`　**维度**：导入导出　**类别**：correctness　**验证置信度**：high

**问题**：The tokenizer treats the `$` of a `$'...'` ANSI-C quoted word as ordinary text and does not decode the escapes, so headers copied from Chrome/Firefox DevTools land with a bogus `$`-prefixed key and un-decoded `\uXXXX`/`\r\n` bytes.

**失败场景**

Chrome DevTools "Copy as cURL" emits `$'...'` whenever a value contains `!`, a quote, a control char or non-ASCII — very common for Cookie/token headers. Verified: `curl 'https://example.com/a' -H $'cookie: a=b' -H $'x-t: 中'` parses to headers `[{key:"$cookie", value:"a=b"}, {key:"$x-t", value:"\\u4e2d"}]`. The request is then sent with a meaningless `$cookie` header and no real `Cookie` header, so the session cookie is dropped and the user gets a 401 with no indication why. Because parseAuthorizationHeader compares `key.toLowerCase() !== "authorization"`, a `$authorization` key also skips Bearer/Basic extraction entirely.

**证据**

```
if ((char === "'" || char === '"') && !quote) {
  quote = char
  continue
}
// '$' before the quote was already appended to `current`, and inside a single
// quote `char === "\\" && quote !== "'"` is false so escapes stay literal
```

**修复**

In tokenizeCurlCommand, when a `'` is encountered while `current === "$"` (i.e. the word starts with `$'`), drop the `$`, enter a dollar-single-quote mode and decode ANSI-C escapes (\n \r \t \\ \' \xHH \uHHHH) before closing the token.

<details><summary>对抗性验证记录</summary>

## 3. [高] No response decompression: any request carrying Accept-Encoding returns a garbled body

- **位置**：`src-tauri/src/lib.rs:2440`　**维度**：Rust/HTTP　**类别**：correctness　**验证置信度**：high

**问题**：reqwest is built without the gzip/brotli/deflate/zstd features, and nothing strips or handles a user-supplied Accept-Encoding header, so a gzip response body is passed straight through String::from_utf8_lossy.

**失败场景**

The flagship workflow (paste a cURL copied from Chrome DevTools) yields a tab with `-H 'accept-encoding: gzip, deflate, br'`. curl-parser keeps every -H verbatim, lib.rs:2306-2318 forwards it, the server answers `content-encoding: gzip`, reqwest (no gzip feature) hands back the raw deflate stream, and lib.rs:2440 lossy-decodes it: the user sees status 200 with a body of U+FFFD garbage and a `size` that is the compressed length. Scripts/tests reading response.body get the same garbage.

**证据**

```
src-tauri/Cargo.toml:29
  reqwest = { version = "0.12", default-features = false, features = ["rustls-tls", "json", "multipart", "socks"] }   # no gzip/brotli/deflate/zstd
lib.rs:2440  let body = String::from_utf8_lossy(&bytes).to_string();
```

## 19. [中] form-urlencoded / form-data append a second Content-Type instead of respecting the user's header

- **位置**：`src-tauri/src/lib.rs:2376`　**维度**：Rust/HTTP　**类别**：correctness　**验证置信度**：high

**问题**：reqwest's RequestBuilder::header() appends, so when the user has an explicit Content-Type row the request goes out with two Content-Type headers (and two Authorization headers when basic/bearer auth is combined with a manual Authorization header).

**失败场景**

Tab has header `Content-Type: application/x-www-form-urlencoded;charset=UTF-8` (extremely common when pasting a cURL from a Chinese/Java backend) and body type form-urlencoded. lib.rs:2376 appends a second `content-type: application/x-www-form-urlencoded`, so hyper writes both header lines. Spring/Tomcat and many WAFs reject the duplicate with 400, or parse only the first. Worse for form-data: user pastes a DevTools cURL that carries `-H 'content-type: multipart/form-data; boundary=----WebKitFormBoundaryAbc'`, switches to the form-data editor, and lib.rs:2386 appends the real boundary as a SECOND content-type; the server reads the first (stale boundary) and fails to find any parts -> 400 / empty $_FILES. Same class at lib.rs:2351/2359: a manual `Authorization: Bearer old` plus auth type bearer sends two Authorization headers.

**证据**

```
lib.rs:2374-2377

        request = request
            .header(CONTENT_TYPE, "application/x-www-form-urlencoded")
            .body(args.body.content);
lib.rs:2386  request = request.multipart(form);   // reqwest multipart() also uses .header(...)
reqwest-0.12.28/src/async_impl/request.rs:223  req.headers_mut().append(key, value);   // header() APPENDS
(contrast: .json() at request.rs:452 checks `if !req.headers().contains_key(CONTENT_TYPE)`, which is why json bodies are unaffected)
```

**修复**

Stop relying on reqwest's appending helpers for auto-set headers. Set them on the HeaderMap built at lib.rs:2306-2335 with entry/or_insert semantics before `.headers(header_map)`: for form-urlencoded insert the content-type only if the user has none; for form-data build the Form first, take `form.boundary()`, and `header_map.insert(CONTENT_TYPE, multipart/form-data; boundary=...)` unconditionally (a user-supplied multipart content-type without our boundary is never correct).         data += chunk
    key = ""

        p = ("tick %d" % i).encode()
        try: c.sendall(b"\x81" + bytes([len(p)]) + p)
        except OSError: print("client gone", flush=True); return
        i += 1; time.sleep(1)

s.bind(("127.0.0.1", 9099)); s.listen(5)
print("listening on ws://127.0.0.1:9099", flush=True)

## 35. [中] ws_disconnect drops the sender without terminating the reader task, so an unresponsive peer leaves the socket and task alive forever

- **位置**：`src-tauri/src/lib.rs:2184`　**维度**：WebSocket/健壮性　**类别**：resource-leak　**验证置信度**：high

**问题**：ws_disconnect removes the write half from ws_pool and sends a Close frame, but the spawned read loop only exits on a Close/Err from the peer; dropping one half of a split stream does not close the connection, so a peer that ignores Close keeps the task, socket and AppHandle alive with no remaining handle to abort it.

**失败场景**

Ten connect/disconnect cycles leave ten orphan sockets and tasks that only die at process exit.

**证据**

```
lib.rs:2186-2194 `if let Some(mut sender) = connections.remove(&connection_id) { ... let _ = sender.send(WsMessage::Close(None)).await; }` - the sink is then dropped; the reader spawned at lib.rs:2095+ loops `while let Some(message) = read.next().await` and only `break`s on Ok(Close)/Err.
```

**修复**

Store the reader task's JoinHandle/AbortHandle alongside the sender (in ws_pool or a parallel map) and abort it in ws_disconnect after sending Close, or race the close handshake against a timeout and abort on expiry. Clear the connection's event queue after the abort rather than before.

<details><summary>对抗性验证记录</summary>

Verified, could not refute the core mechanism. (1) lib.rs:2097 spawns the read loop and discards the JoinHandle; no abort handle, cancellation token, or timeout exists anywhere for WS reader tasks. The loop at lib.rs:2098-2154 breaks only on Ok(Close)/Err from the peer. (2) lib.rs:2187-2193 removes the sink, sends Close(None) via SinkExt::send (poll_ready/start_send/poll_flush only, never poll_close), then drops the sink. (3) Dropping the sink does NOT close the connection: futures-util 0.3.32 (Cargo.lock:1207) stream/split.rs implements split() as BiLock::new(s) and SplitSink has no Drop impl, so the inner WebSocketStream (and its TCP/TLS socket) stays alive via the SplitStream's BiLock arm. ## 42. [低] ws_suppressed_disconnect_pool grows forever in the packaged app because publish_ws_event never reaches the drain path when an AppHandle is present

- **位置**：`src-tauri/src/lib.rs:2189`　**维度**：WebSocket/健壮性　**类别**：resource-leak　**验证置信度**：high

**问题**：ws_disconnect always inserts a suppression marker, but publish_ws_event returns early whenever `app` is Some, so in the Tauri build the marker is never removed - the global map accumulates one entry per disconnect for the process lifetime.

**失败场景**

In the shipped macOS app (always the `Some(app)` path) every Connect/Disconnect cycle inserts a UUID key into WS_SUPPRESSED_DISCONNECT_EVENTS that nothing ever removes; a session that reconnects on a retry loop (1/second while debugging a flaky endpoint) adds ~3,600 dead entries per hour, and each later ws_disconnect locks the ever-growing map. **证据**

```

```

<details><summary>对抗性验证记录</summary>

### `src-tauri/src/lib.rs:645` — Window state is written to disk synchronously on every Resized event

### `src/stores/request.ts:212` — cancelRequest() clears isLoading unconditionally, killing the spinner of a newer in-flight send in the same tab

### `src/stores/request.ts:220` — isLoading stuck true forever when a response arrives while a cancel is in flight and the cancel then fails

### `src-tauri/src/lib.rs:1491` — Rust redact_sensitive_text only parses urlencoded bodies, so JSON request bodies are saved to collection files in plaintext

Note the direction of the real usability wart is the opposite of the finding: a saved `form-urlencoded` body `password=hunter2` is already silently rewritten to `password=[redacted]`, destroying the saved definition. "Extending" that to JSON would spread the corruption, not close a leak.

5) The sanctioned path for repeatable secrets is explicitly "save to a collection + {{var}} templates", which requires the body to be persisted as typed.

### `src/stores/request.ts:104` — Pre-request script variable writes are committed to the live environment before the failure check, and retarget the in-flight request
