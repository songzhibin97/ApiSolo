## Summary

ApiSolo 发出去的字节和收回来的字节，现在都和用户在界面上看到的不是同一份东西。本切片让「Headers / Body / Auth 三个面板显示的内容」和「线上真实报文」一致，让响应体在呈现给用户之前被正确解压、按正确字符集解码，解不出文本或压缩方式解不了的响应一律如实标成二进制；并且让「点下 Send 到看到结果」这段时间真正受一个统一的 30 秒预算约束、界面上显示的总耗时就是这段时间本身。

## 范围

实现范围只覆盖 `src-tauri/src/lib.rs` 的 HTTP 执行段（`send_request` 及其被调用方）与对应的 Rust 测试。

## Problem

按真实用户撞上的频次排序：

1. **响应从不解压**。产品的旗舰路径是「粘贴一条从 Chrome DevTools 复制的 cURL」，而这种 cURL 一定带着 `accept-encoding: gzip, deflate, br`（2024 年以后的 Chrome 还会带 `zstd`）。cURL 导入原样保留这个 header，服务端于是返回 `content-encoding: gzip`，ApiSolo 把压缩流直接当文本显示。用户看到状态 200 + 一屏 U+FFFD，没有任何东西提示失败。

2. **响应体强制按 UTF-8 解码**。响应头里的 `charset=` 被读出来了、原样回传给 UI 了，却从来没有被用来解码。`text/html; charset=gb2312` 的每个汉字都变成 U+FFFD，而且这份已经损坏的字符串还会被写进 `history.jsonl`。`image/png` / `application/zip` 之类的二进制响应同样被当文本渲染成垃圾，界面上没有任何「这是二进制」的提示。

3. **自动附加的请求头是「追加」而不是「覆盖」**。用户自己写的 `Content-Type` 行和应用算出来的那一个会同时上线，且用户那一行在前。最确定会坏的两种形态：form-data 时用户 header 里的旧 boundary 排在真 boundary 之前，按首值优先解析的服务端一个 part 都找不到；Auth 面板选了 bearer/basic 而 header 表里还有一行手写的 `Authorization` 时，手写那行在前，于是 **Auth 面板变成了一个什么都不做的控件**，这正踩在「UI 不许说谎」上。

4. **JSON body 被重新序列化**。用户敲的 JSON 会被解析成 `serde_json::Value` 再序列化后发出：key 按字母重排、缩进和换行被压掉、重复 key 被丢掉、超过 u64 的整数字面量退化成浮点。对原始报文体做签名的接口一律返回签名错误，而前置脚本拿到的是未被改写的原文，用户从两边都看不出差异。

5. **传输失败的错误信息全都一样**。自签名证书被拒、超时、连接中途被重置，最终都只显示 `Request failed: error sending request for url (...)`，真正的原因在 `Error::source()` 链上被丢掉了。

6. **预连接探测能替真实请求做生死判定，而且它的耗时不在任何预算里**。为了测 DNS/TCP 耗时，每次发送前会额外连一次目标主机。这段探测只试第一个解析出来的地址、DNS 与连接都没有任何时间上限、失败时用 `?` 把整个请求判死。于是：第一个 A 记录不可达时 curl 能通、ApiSolo 不能；目标静默丢 SYN 时用户要等约 75 秒而不是配置的 30 秒；DNS 服务器不响应时更是无限期卡住。

7. **零查询参数时 URL 仍带一个尾随 `?`**。`GET /v1/users` 被发成 `GET /v1/users?`。用户界面上看不到它，只在服务端访问日志、按原始 request-target 匹配的 CDN/WAF 规则里才暴露。

## Behavior

以下每条都可独立测试，编号与 `TECH.md` §4.1 的测试计划一一对应。括号里标注它对应 `specs/BACKLOG.md` 的哪一行。**验证方式不足的条目（第 36、49 条）在条目内显式声明，不含糊过去。**

### 响应解压（backlog `lib.rs:2440` high）

1. 响应头为 `Content-Encoding: gzip` 时，用户看到的是解压后的正文。
2. 响应头为 `Content-Encoding: br` 时，用户看到的是解压后的正文。
3. 响应头为 `Content-Encoding: deflate` 且报文体是 zlib 流（RFC 1950）时，用户看到的是解压后的正文。
4. 响应头为 `Content-Encoding: deflate` 但报文体是裸 deflate 流（RFC 1951，部分服务端的历史行为）时，同样解压成功——不能因为不带 zlib 头就判失败。
5. 编码名的匹配忽略大小写与首尾空白（`GZIP`、` gzip `、`Br` 都能识别）。
6. `x-gzip` 被当作 `gzip` 的别名识别。
7. 多成员拼接的 gzip 流（多个 gzip member 首尾相接）被完整解压，而不是只解出第一段。
8. 解压成功后：响应头列表里不再有 `Content-Encoding` 与 `Content-Length`（它们描述的是压缩前的字节，留着就是把过期信息摆在解码后的正文旁边），`size` 是解压后的字节数。
9. **编码列表的判定规则。** `Content-Encoding` 按 HTTP 语义收集：多行 `Content-Encoding` 字段与单行逗号列表**等价**，都是同一个有序编码列表。规则逐条：
   - 头缺失、或规范化后没有任何有效 token（例如整行是空的、只有逗号和空白）、或全部 token 都是 `identity` —— 视为**无编码**，不解压。「全空 token 等同无编码」是有意契约，不是漏判。
   - `identity` 从列表中剔除后**恰好剩下一个受支持编码** —— 解压。因此 `identity, gzip` 会被正确解压。
   - 剩下**两个或更多** token —— 视为**无法解码**，无论它们是否都受支持。重复项**不去重**（`gzip, gzip` 是真实的双重压缩，去重会解错），`gzip, br` 与分成两行的 `gzip` + `br` 结论相同。
   - 剩下一个但不是受支持编码（例如 `zstd`），或 token 带参数（例如 `gzip;q=1.0`——`Content-Encoding` 在语法上不允许参数，出现即视为畸形）—— 视为**无法解码**。
10. `Content-Encoding` 的字段值不是合法 UTF-8 时（畸形头，可由代理或被入侵的服务端产生），视为**无法解码**；绝不因为「读不出字符串」就退化成「没有编码」。
11. 「无法解码」的三条后果同时成立，缺一不可：**(a)** 报文体字节不做任何变换；**(b)** `Content-Encoding` 与 `Content-Length` 原样保留在响应头里，用户从界面就能看出「有压缩、且没被解开」；**(c)** 正文位置**无条件**给出一行明确标明「压缩响应未被解码」及其编码列表的提示，并标记为二进制。绝不允许一段未解码的压缩字节因为碰巧是合法 UTF-8 就被当成正文显示。
12. 无编码（含 `identity`）时，**解压层不改变任何字节，也不删除任何响应头**；随后正文照常走第 17–24 条的文本/二进制处理。（这里**不**承诺「正文与旧版本逐字节一致」——旧版本对 GBK 正文产生 U+FFFD、对非法 UTF-8 做有损替换，新版本会正确解码或如实标成二进制。那是第 17–22 条要求的改进，不是回归。）
13. 声明了某种受支持编码但报文体损坏 / 被截断时，请求以错误结束，错误信息里点名是哪种编码解码失败并带上底层原因；不会把半截或乱码的正文当成功结果展示。
14. 解压后的字节数**恰好等于**上限时，请求正常成功——上限的含义是「允许到这里」，不是「到这里就算超」。
15. 解压后的字节数**超过**上限时，请求以错误结束，错误信息里点明这个上限；不会把被截断的正文当成完整正文展示。
16. ApiSolo 自己不会添加任何 `Accept-Encoding` 请求头。线上带的 `Accept-Encoding` 完全等于 Headers 表里写的那一行；Headers 表里没有这一行时，线上也没有。

### 响应体解码（backlog `lib.rs:2440` med）

17. 响应 `Content-Type` 带 `charset=` 参数时，按该字符集解码。`gb2312` / `gbk` / `shift_jis` / `iso-8859-1` 的正文都能还原成正确文本。
18. `charset=` 参数的解析对真实报文里出现的各种写法都成立：参数名大小写不敏感（`Charset=` / `CHARSET=`）、取值可以带双引号、取值本身大小写不敏感、`Content-Type` 里同时存在其他参数时（无论排在 `charset` 之前还是之后）都不受影响、`xcharset=` 这类子串不会被误认。
19. `Content-Type` 里没有 `charset=` 参数（或整个头缺失）时，按 UTF-8 解码。
20. `charset=` 存在但不是一个可识别的编码名时，退回 UTF-8 解码；若 UTF-8 也解不出，则按第 21 条处理。不做任何猜测式的编码嗅探。
21. 字节序列在选定编码下不是合法文本时，响应被如实报告为二进制：正文位置是一行固定格式、明确标明这是 ApiSolo 提示而非服务端内容的说明（含字节数与 `Content-Type`），响应对象上带一个机器可读的「二进制」标记。任何情况下 ApiSolo 都不再用 U+FFFD 替换字符去顶替解不出来的字节。
22. 报文体中含 `0x00` 字节时按二进制处理，即使选定编码（例如 `iso-8859-1`）在形式上能接受它。
23. 报文体为空时，正文是空字符串、标记为文本、`size` 为 0——空响应不是二进制响应。
24. `size` 恒等于「解压之后、字符集解码之前」的字节数。它不随解码出的字符数变化，也不随文本/二进制的判定结果变化。

### 自动附加的请求头（backlog `lib.rs:2376` med）

25. body 类型为 form-data 时，线上有且只有一个 `Content-Type`，其值恒为应用实际用于分段的那个 boundary；即使 Headers 表里写了自己的 `Content-Type`，也以应用的为准（对 multipart 来说，只有应用自己的 boundary 是正确值）。
26. body 类型为 form-urlencoded 时，线上有且只有一个 `Content-Type`。Headers 表里写了就用用户的（连同用户的 `charset` 后缀一起保留）；没写才由应用补上 `application/x-www-form-urlencoded`。
27. body 类型为 json 时，线上有且只有一个 `Content-Type`。Headers 表里写了就用用户的；没写才由应用补上 `application/json`。
28. body 类型为 raw / binary / none 时，ApiSolo 不添加任何 `Content-Type`；Headers 表里有几行就发几行。
29. Auth 类型为 basic 或 bearer 时，线上有且只有一个 `Authorization`，值来自 Auth 面板；Headers 表里手写的 `Authorization` 被它取代。Auth 面板一旦被选中就是明确指令，绝不允许出现「面板设了值但线上不生效」。
30. Auth 类型不是 basic / bearer 时（`none` 或 `api-key`），Headers 表里手写的 `Authorization` 原样发出——有几行发几行、顺序不变，ApiSolo 既不添加、也不合并、也不改写。想让手写 header 生效，把 Auth 面板切回 `none` 即可，这是用户侧唯一需要知道的规则。
31. Auth 类型为 api-key 且投放位置是 header 时，行为不变：该名字的请求头有且只有一个，值来自 Auth 面板。

### 请求体保真（backlog `lib.rs:2369` med）

32. body 类型为 json 时，线上的字节与编辑器里的文本逐字节相同：key 顺序、缩进与换行、重复 key、数字字面量形式、超长整数全部保持原样。
33. body 类型为 json 但内容不是合法 JSON 时，请求在发出任何字节之前被拒绝，错误信息与当前版本一致（`Invalid JSON body: ...`）。想发故意畸形的 JSON，用 raw。

### 失败诊断（backlog `lib.rs:2410` med）

34. 传输阶段失败时，错误信息包含完整的原因链，因此 TLS 证书被拒、连接被拒、DNS 失败、超时四种情况彼此可区分，而不是同一句话。
35. 读取响应体阶段失败时（例如服务端声明的 `Content-Length` 与实际发送量不符后断开），错误信息同样包含完整的原因链。

### 时间预算与耗时呈现（backlog `lib.rs:2337` med）

36. **预连接探测在结构上不可能决定请求的成败。** 探测的对外接口只能返回一对耗时数字，没有任何失败通道可以外泄——DNS 失败、地址全不可达、预算到点、内部任务崩溃，一律收敛成「测不到」（对应分量记 0），请求照常发出，用户看到的错误只可能来自 HTTP 客户端。（**验证方式如实声明**：这一条没有单行变异可以违反它——要违反必须改函数签名，那是结构性改动。它由类型保证 + 代码评审把关，见 `TECH.md` §4.3。rev3 曾用「已关闭的 loopback 端口」为它写过一条回归测试，那条测试**永远不会红**，已删除。）
37. 探测会依次尝试解析出的每一个地址，因此第一个地址不可达、第二个可达的主机仍然能被测到（并且请求本来就能成功）。
38. 探测的时间预算在待尝试的地址之间公平切分：第一个地址即使是「静默丢包的黑洞」，也只能用掉属于它的那一份，后面的地址一定还有机会被尝试。前面的地址快速失败时省下的时间，归后面的地址。
39. 预算耗尽后不再发起任何新的连接尝试。
40. 探测的预算覆盖 **DNS 解析在内的整段探测**，不只是连接动作。DNS 服务器不响应时，探测在预算到点后放弃、把耗时记为 0，请求照常发出。
41. **一次发送只有一个总预算。** 从点下 Send 到拿到结果，预连接探测、建连与传输、读完响应体、响应体拷贝、解压与字符集解码**共享**同一个 30 秒预算：每一段开始前都会读一次**当时**的剩余预算并把它传给这一段。探测最多用掉其中 5 秒，剩余不足 5 秒时只能用掉剩余的那部分。
    **不受打断的同步步骤（完整枚举，不是「唯一一处」），分两类**：
    - **发送前的同步步骤**——HTTP 客户端构建、URL 与请求头构建、把用户自己提供的 body 编码成字节（JSON 校验、内联 base64 解码、multipart 拼装）、请求对象构建与请求头归一化。它们不会被中途叫停，但耗时**计入**预算，且**后面还有检查点**（第 43 条）会立刻发现预算已尽。只有当**单独一步**本身就超过预算时，那一步才会跑完。
    - **解码之后的结果组装**——遍历响应头生成键值对、算耗时、构造返回值。它**后面没有任何检查点**，因此是一段**明确接受的有界近似**：它的时长由响应头数量决定（这一项确实受远端影响，只是被 HTTP 层自身的请求头总量上限所限），实践中远小于预算粒度，但本规格**不声称它「永远不会撞线」**——只声称它未被覆盖、且代价有界。
42. HTTP 请求本身的超时是「**请求对象构建与请求头归一化完成之后**剩余的那部分预算」，而不是又一个独立的 30 秒，也不是构建之前就算好的数字。（rev4 在构建之前取值，等于把构建耗时重复留给了 HTTP 阶段。）
43. 请求还没发出去、预算就已经耗尽时，请求**不会**被发送；用户拿到一条点明这个上限的错误，而不是一个从零开始重新计时的 30 秒等待。
44. 响应体的**拷贝、解压与字符集解码整体**受剩余预算约束：这段工作超出预算时，请求以错误结束，而不是让用户继续等下去。（两点如实说明：① 一个本来能成功的巨大压缩响应会在预算边界被放弃，这是「30 秒就是 30 秒」的对价，也是压缩炸弹在 CPU 维度上的兜底；② 结束时刻是「到点后尽快」而不是「严格卡在 deadline 那一毫秒」——零剩余预算下计时器与解码任务谁先就绪没有强保证，所以承诺是上界近似，不是精确切断。）
45. **界面上的总耗时就是用户实际等待的时间**，由整段操作实测得出，不由 DNS / TCP / 下载三段相加合成。因此「第一个地址是黑洞、探测在它上面耗了两秒半」这类等待不会从总耗时里消失，「所有地址都连不上、TCP 分量记 0」也不会让那段等待凭空蒸发。总耗时恒不小于各分段之和。
46. 启用代理时，探测被整体跳过，`dnsLookup` 与 `tcpConnect` 保持 0。（回归护栏：探测会直连目标主机，在「必须走代理、目标不可直连」的网络里跑它就是把请求判死。）
47. `tlsHandshake` 与 `ttfb` 在任何情况下都保持 0。（回归护栏：这一层拿不到可靠数据，写 0 是既定决策。）测量失败或被跳过的字段一律是 0，不用任何方式反推出「看起来合理」的数字。

### 请求目标（backlog `lib.rs:2291` low）

48. 没有任何一个启用且键名非空的查询参数、且用户输入的 URL 本身不带 `?` 时，线上的 request-target 不带查询串、也不带尾随 `?`。用户自己在 URL 里敲的 `?` 原样保留。

### 运行时行为

49. 解压与字符集解码是纯 CPU 工作，不占用异步执行线程。一个体积很大的压缩响应在解码期间，取消按钮、WebSocket 事件、以及其他正在进行的请求都不会被冻住。（**验证方式如实声明**：这一条**没有**有效的自动化变异检查，见 `TECH.md` §4.3 的验证缺口登记；它由代码评审把关。）

## Non-goals

以下都是既定决策或已知既有债，本切片不碰，也不重新讨论：

- **`tlsHandshake` / `ttfb` 恒为 0**。这一层拿不到可靠的分阶段事件，早期用 `ttfb / 2` 反推被判定为伪精度。第 47 条是护栏，不是待办。
- **`.no_proxy()` 与「启用代理跳过预探测」**。两者都是从真实 502 根因倒推出来的，不动。第 46 条是护栏。
- **30 秒这个数值本身**。第 41–44 条改的是「这个预算是否被统一执行」，不是数值大小，更不是把它做成可配置项。
- **让第 41 条枚举的那些同步步骤可被中途打断**。把 body 编码、请求构建、结果组装拆成可让出的分块是另一个数量级的改动，本切片只保证它们的耗时被计入预算、超支在下一个检查点被发现。
- **在结果组装之后再加一次预算检查**。刻意不做，理由是代价不对称而不是「它不可能撞线」：那一步一旦撞线，代价是把一个已经完整收到、完整解码成功的响应整个丢掉；而它的时长由响应头数量决定，被 HTTP 层自身的请求头总量上限所限，量级远小于预算粒度。第 41 条因此把它明确列为「没有后继检查点的有界近似」，而不是假装它被覆盖，也不假装它不可能发生。
- **上传文件必须 base64 内联，裸文件系统路径无条件拒绝**。本切片改的是同一个函数，但这三道防线一行不改。
- **未压缩响应体没有内存上限**。这是已知且已接受的债。第 14/15 条只给「解压输出」加上限——因为压缩炸弹是本切片新引入的失败模式（见 `TECH.md` §5.2）；原样返回路径的上限交给后续切片。
- **zstd 解压**。本切片不做。zstd 响应走第 9/11 条的「无法解码」路径：不解压、保留 `Content-Encoding: zstd`、按二进制呈现并说明原因。
- **把未解码的原始压缩字节交还给用户**（另存为文件 / base64 展示）。前端的正文字段是 `string`，本切片不改这个类型；第 11 条承诺的是「解压层不改变原始字节」与「UI 拿到一个明确的 marker」，不是「用户能拿回原始字节」。
- **剥离正文开头的 BOM**、**从 HTML `<meta charset>` 嗅探编码**、**在没有 `charset` 时对内容做编码嗅探**。都是猜测式行为，本切片一律不做。
- **二进制响应在界面上的呈现**（预览、另存为文件、base64 展示、本地化文案），以及**二进制标记在历史里的持久化与重放**。本切片只产出机器可读的标记；消费它的前端与历史链路改动是跨切片依赖，见 `TECH.md` §6。
- **错误信息里回显的 URL 中的密钥脱敏**。今天 `Request failed: ... for url (https://x/?api_key=SECRET)` 就会带出查询串里的密钥；本切片的原因链改造不会让它变好也不会变差，这条边界属于 D01。
- **移除预连接探测本身**。移除它会让 `dnsLookup` / `tcpConnect` 对所有人恒为 0，是产品能力的倒退。
- **`raw` / `binary` body 的自动 `Content-Type`**。今天不加，改了就是改变现存可用请求的线上字节。
- **`Cargo.toml` / `Cargo.lock` 里依赖声明以外的任何内容**（A11 例外的边界），以及 **`src-tauri/src/lib.rs` 的持久化段、密钥 vault 段、WebSocket 段、history 段**（分别属于 D03 / D03 / D04 / D01）。
