# ApiSolo — 仓库硬规则

本文件**只收录在本仓库真实发生过、并造成了返工或证据失效的**违规。通用工程纪律不写在这里，它们在全局记忆里。

每条规则都要带上它诞生的那次事故——没有事故的规则会被当成教条而被忽略。

---

## R1 — 评审在飞行途中，被评审的产物一个字都不能改

**规则**

1. 任何产物（spec、实现、文档）交付一版后进入**只读**，由 owner 固化成一个 commit 作为 freeze 锚点。
2. 独立评审开始后到结论回来之前，该产物不得修改。作者发现自己写错了，**先报 owner**，由 owner 决定中止评审重跑、还是记进 disposition 下一轮一起改。
3. 跨切片的协调结论**先报 owner 裁定，再落盘**。跨切片措辞是两份 spec 共同的契约，任一方单方面改写会让另一方的评审结论一并失效。
4. 只有 owner 下发修订指令时，才是作者的写入窗口。

**事故（2026-08-18）**

同一天连续发生两次。owner 于 12:02:04 将 D01 的 rev3 交付独立评审；起草者在 12:08:44 与 12:09:15 分别修改了 `PRODUCT.md` 与 `TECH.md`。D03 同样：评审 12:09:41 启动，起草者随后做了三处改动。两次改动的**内容本身都是对的**，都是与另一个切片协调后的正确结论——问题纯粹在时序。

**为什么它有害**

评审结论会指向一个磁盘上已不存在的版本，于是无法判断「评审没报这个问题」到底是因为不存在，还是因为它读的是旧文本。这直接摧毁了 owner-pipeline 的核心资产：三条证据流（实现者自检 / owner 亲跑 gate / 评审结论）互相独立且互不顶替。一条证据的时间锚点一旦模糊，它就不再是证据。

**责任归属**：这两次的根因是 owner 派单时没有交代规约，不是起草者的过失。规则写在这里是为了下次不再依赖某个人记得。

## R2 — 「我验证过」必须写明验证的是什么

**规则**

声称实跑验证时，必须写明跑的是**哪个东西**。特别是：验证一个外部工具的行为，必须跑那个工具本身，而不是跑自己对它的实现。

**事故（2026-08-18）**

D06 的 spec 声称已实跑验证 `--data-urlencode` 的编码行为，写的是空格编码成 `%20`。owner 在本机跑真实 `curl 8.7.1`，得到的是 `q=a+b%26c`——空格是 `+`。起草者跑的是自己的实现，不是 curl。若未被抓到，这个错误会连同一条断言一起被冻结进回归测试，从此以「已验证」的姿态长期存在。

同一天另一次：`docs/review/REVIEW-2026-08-18.md` §28 的对抗验证记录称某个 JSON 输入脱敏后是安全的，实跑为非法 JSON。**一份写着「已对抗验证」的文档，其个别条目仍然可能是错的。**

## R3 — 变异检查列必须是可编译的单行改动，且必须真的能杀死测试

**规则**

每条不变式的 mutation killer 必须是一个**能编译的单行 patch**，并写明改动后**哪一条断言会红**。写不出来就说明这条测试是同义反复，重新设计测试；两条不变式确实共用一个 killer 时如实标注，不许编造第二个。

**事故（2026-08-18）**

D01 与 D02 的规格都声称「每条不变式都有可执行的变异 gate」，评审实跑后查出多条 **survivor**：删掉正则的 `lastIndex = 0` 复位后，幂等测试仍然全绿；另有多条 killer 根本编译不过（引用了尚未定义的变量、不符合目标函数签名）。

D01 深挖后发现根因比「漏了个复位」更根本：`exec` 循环命中即 `return` 会留下非零 `lastIndex`，于是幂等断言的结果**取决于该测试在文件中的位置**。修法不是补复位，而是把正则改成函数内构造，从结构上消除共享状态。

**为什么它有害**

放行的话，我们会拿着一张「每条不变式都有测试保护」的表，而表里有几行是假的。一张不可信的验收表比没有表更危险。

## R4 — 不得把其他 agent 的陈述当作事实写进持久产物

**规则**

需要引用另一个 agent 的产出时，二选一：**亲自确认它存在且内容如此**，或者写成转述并标明未验证来源（「据 D03 称」）。不许用陈述句把听来的东西写成既成事实。

**事故（2026-08-18）**

D01 的 spec 写下「`specs/D03-persistence/TECH.md` §2.2 记录了本切片的锁契约」。写下的那一刻，`specs/D03-persistence/` 在该工作树里**根本不存在**——对方在独立 worktree 里工作。一条 `ls specs/` 即可发现。

**为什么它有害**

起草者自己的定性最准确：两个切片**互相把对方的口头陈述当作可引用的事实写进了各自的 spec，于是两份文档在没有任何一方验证的情况下产生了耦合**。这比单纯的悬空引用更糟——悬空路径至少会在有人点开时暴露，而未经验证的相互引用会一直读起来像是已经对齐过了。

这也是 R1 第 3 条（跨切片结论先经 owner）的真正价值所在：只有 owner 同时看得到两份产物的真实状态。

**最难自觉执行的形态：未验证的推断伪装成因果解释**

同一位起草者，在**专门记录这条规则的那段事故说明里**，又写了一句未验证的断言——「（对方在独立 worktree 里）」。那是它从「`ls specs/` 看不到那个目录」推出的合理猜测，后来被 owner 独立佐证为真，但写下的当时并未核实。

它自己的定性是这条规则最有用的补充：

> 那句话在我写的时候感觉不像一个断言，感觉像在**解释一个显而易见的原因**。未验证的推断伪装成因果解释的时候最难被自己抓住——比伪装成引用还难。

所以 R4 的适用面不止「引用对方的产出」。**任何写进持久产物的因果解释，只要它的依据是推断而非核实，就要按转述标注。** 引用至少长得像引用，会提醒你去查；因果解释读起来像理解，不像主张。

## R5 — 跨文档引用只能引用行为，不得引用任何外部标识符

**规则**

判据不是「它是不是号码」，而是**「它的身份是否由另一个文档单方面决定、且可能在你不知情时改变」**。章节号、条目 ID、文件路径，全部在内。

- **跨切片引用**（一份 spec 指向另一份 spec）：只描述行为，不带任何标识符。
- **指向 `specs/BACKLOG.md` 的裁定台账**（A1–A10）：**允许**。该表由 owner 维护，只追加不重编号，owner 为其稳定性负责——这正是它存在的意义。
- **指向切片内的局部枚举**（如某切片的交接项 `C1`）：不允许，那些是会随 scope 调整重排的临时列表。
- **同一份文档内部的自引用**：不受限。

**事故（2026-08-18）**

D01 的 spec 在四处引用了 D03 的章节号与条目 ID。而 D01 自己的不变式编号在三轮修订里走过 27 → 34 → 39，D03 当时尚未定稿——任何这类指针都必然烂掉，区别只是烂在评审时还是半年后。`specs/BACKLOG.md` 的 `REVIEW #n` 编号也已经 churn 过一次（整体偏移 +2）。

初版规则只写了「不得引用章节号」，范围太窄，是起草者主动扫描作用面时发现还有条目 ID 和文件路径两种同类变体。
