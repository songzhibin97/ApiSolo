# ApiSolo — 仓库硬规则

本文件**只收录在本仓库真实发生过、并造成了返工或证据失效的**违规。通用工程纪律不写在这里，它们在全局记忆里。

每条规则都要带上它诞生的那次事故——没有事故的规则会被当成教条而被忽略。

---

## R1 — 评审在飞行途中，被评审的产物一个字都不能改

**规则**

1. 任何产物（spec、实现、文档）交付一版后进入**只读**，由 owner 固化成一个 commit 作为 freeze 锚点。
2. 独立评审开始后到结论回来之前，该产物不得修改。作者发现自己写错了，**先报 owner**，由 owner 决定中止评审重跑、还是记进 disposition 下一轮一起改。
3. 跨切片的协调结论**先报 owner 裁定，再落盘**。跨切片措辞是两份 spec 共同的契约，任一方单方面改写会让另一方的评审结论一并失效。
4. 只有 owner 下发修订指令时，才是作者的写入窗口。

**事故（2026-08-18）**

同一天连续发生两次。owner 于 12:02:04 将 D01 的 rev3 交付独立评审；起草者在 12:08:44 与 12:09:15 分别修改了 `PRODUCT.md` 与 `TECH.md`。D03 同样：评审 12:09:41 启动，起草者随后做了三处改动。两次改动的**内容本身都是对的**，都是与另一个切片协调后的正确结论——问题纯粹在时序。

**为什么它有害**

评审结论会指向一个磁盘上已不存在的版本，于是无法判断「评审没报这个问题」到底是因为不存在，还是因为它读的是旧文本。这直接摧毁了 owner-pipeline 的核心资产：三条证据流（实现者自检 / owner 亲跑 gate / 评审结论）互相独立且互不顶替。一条证据的时间锚点一旦模糊，它就不再是证据。

**责任归属**：这两次的根因是 owner 派单时没有交代规约，不是起草者的过失。规则写在这里是为了下次不再依赖某个人记得。

## R2 — 「我验证过」必须写明验证的是什么

**规则**

声称实跑验证时，必须写明跑的是**哪个东西**。特别是：验证一个外部工具的行为，必须跑那个工具本身，而不是跑自己对它的实现。

**事故（2026-08-18）**

D06 的 spec 声称已实跑验证 `--data-urlencode` 的编码行为，写的是空格编码成 `%20`。owner 在本机跑真实 `curl 8.7.1`，得到的是 `q=a+b%26c`——空格是 `+`。起草者跑的是自己的实现，不是 curl。若未被抓到，这个错误会连同一条断言一起被冻结进回归测试，从此以「已验证」的姿态长期存在。

同一天另一次：`docs/review/REVIEW-2026-08-18.md` §28 的对抗验证记录称某个 JSON 输入脱敏后是安全的，实跑为非法 JSON。**一份写着「已对抗验证」的文档，其个别条目仍然可能是错的。**

## R3 — 变异检查列必须是可编译的单行改动，且必须真的能杀死测试

**规则**

每条不变式的 mutation killer 必须是一个**能编译的单行 patch**，并写明改动后**哪一条断言会红**。写不出来就说明这条测试是同义反复，重新设计测试；两条不变式确实共用一个 killer 时如实标注，不许编造第二个。

**事故（2026-08-18）**

D01 与 D02 的规格都声称「每条不变式都有可执行的变异 gate」，评审实跑后查出多条 **survivor**：删掉正则的 `lastIndex = 0` 复位后，幂等测试仍然全绿；另有多条 killer 根本编译不过（引用了尚未定义的变量、不符合目标函数签名）。

D01 深挖后发现根因比「漏了个复位」更根本：`exec` 循环命中即 `return` 会留下非零 `lastIndex`，于是幂等断言的结果**取决于该测试在文件中的位置**。修法不是补复位，而是把正则改成函数内构造，从结构上消除共享状态。

**为什么它有害**

放行的话，我们会拿着一张「每条不变式都有测试保护」的表，而表里有几行是假的。一张不可信的验收表比没有表更危险。

## R4 — 不得把其他 agent 的陈述当作事实写进持久产物

**规则**

需要引用另一个 agent 的产出时，二选一：**亲自确认它存在且内容如此**，或者写成转述并标明未验证来源（「据 D03 称」）。不许用陈述句把听来的东西写成既成事实。

**事故（2026-08-18）**

D01 的 spec 写下「`specs/D03-persistence/TECH.md` §2.2 记录了本切片的锁契约」。写下的那一刻，`specs/D03-persistence/` 在该工作树里**根本不存在**——对方在独立 worktree 里工作。一条 `ls specs/` 即可发现。

**为什么它有害**

起草者自己的定性最准确：两个切片**互相把对方的口头陈述当作可引用的事实写进了各自的 spec，于是两份文档在没有任何一方验证的情况下产生了耦合**。这比单纯的悬空引用更糟——悬空路径至少会在有人点开时暴露，而未经验证的相互引用会一直读起来像是已经对齐过了。

这也是 R1 第 3 条（跨切片结论先经 owner）的真正价值所在：只有 owner 同时看得到两份产物的真实状态。

**最难自觉执行的形态：未验证的推断伪装成因果解释**

同一位起草者，在**专门记录这条规则的那段事故说明里**，又写了一句未验证的断言——「（对方在独立 worktree 里）」。那是它从「`ls specs/` 看不到那个目录」推出的合理猜测，后来被 owner 独立佐证为真，但写下的当时并未核实。

它自己的定性是这条规则最有用的补充：

> 那句话在我写的时候感觉不像一个断言，感觉像在**解释一个显而易见的原因**。未验证的推断伪装成因果解释的时候最难被自己抓住——比伪装成引用还难。

所以 R4 的适用面不止「引用对方的产出」。**任何写进持久产物的因果解释，只要它的依据是推断而非核实，就要按转述标注。** 引用至少长得像引用，会提醒你去查；因果解释读起来像理解，不像主张。

## R5 — 跨文档引用只能引用行为，不得引用任何外部标识符

**规则**

判据不是「它是不是号码」，而是**「它的身份是否由另一个文档单方面决定、且可能在你不知情时改变」**。章节号、条目 ID、文件路径，全部在内。

- **跨切片引用**（一份 spec 指向另一份 spec）：只描述行为，不带任何标识符。
- **指向 `specs/BACKLOG.md` 的裁定台账**（A1–A10）：**允许**。该表由 owner 维护，只追加不重编号，owner 为其稳定性负责——这正是它存在的意义。
- **指向切片内的局部枚举**（如某切片的交接项 `C1`）：不允许，那些是会随 scope 调整重排的临时列表。
- **同一份文档内部的自引用**：不受限。

**事故（2026-08-18）**

D01 的 spec 在四处引用了 D03 的章节号与条目 ID。而 D01 自己的不变式编号在三轮修订里走过 27 → 34 → 39，D03 当时尚未定稿——任何这类指针都必然烂掉，区别只是烂在评审时还是半年后。`specs/BACKLOG.md` 的 `REVIEW #n` 编号也已经 churn 过一次（整体偏移 +2）。

初版规则只写了「不得引用章节号」，范围太窄，是起草者主动扫描作用面时发现还有条目 ID 和文件路径两种同类变体。

## R6 — 会静默退化的 fixture，测试必须先自检 fixture 再断言行为

**规则**

当测试的输入本身可能在**写入或复制过程中被解释掉**（转义序列、不可见字符、行尾、编码），测试要先断言「我的输入确实还是我想要的那个输入」，再断言行为。

不要靠「下次写的时候小心点」。如果退化来自工具链而非笔误，小心是无效的对策——**换掉依赖**：改用运行时构造（例如用 `String.fromCharCode(92)` 拼出反斜杠）而不是手写字面量，并在文档里改用一个不会被任何环节解释的替身符号。

**事故（2026-08-18）**

D01 的规格声称对比「普通键 `password`」与「转义键 `\u0070assword`」，但文件里两边**实际都是普通的 `password``**——反斜杠在写入时被吃掉了。后果：照这份 fixture 写出的测试，把 `isSensitiveKey(decodeJsonKey(raw))` 换成 `isSensitiveKey(raw)` 仍然全绿，也就是那条不变式**什么都没有证明**。

起草者修复时反斜杠**又被吃了一次**，`String.raw` 也没救回来，最后是 `od -c` 做字节级核对才发现。进一步探针显示这是系统性的：该写入链路会把合法转义解释掉，而非法转义反而原样保留。

**为什么它有害**

这是 R3（killer 必须真能杀死测试）的一个更隐蔽的变体。killer 杀不掉至少还能在应用 mutant 时被发现；**fixture 退化则让测试一路绿着通过，看起来是最健康的状态**。一个断言了错误输入的测试，比没有这条测试更坏——它占着「这条不变式已被覆盖」的位置。

## R7 — 变异检查用来验证设计，不用来塑造设计；但别把这条规则用错地方

**规则**

写不出 killer 时，正确的反应是**重新设计测试**，不是**弱化产品**。

**但这条规则只禁止「让产品变差」。** 它不禁止为了可测性添加**对产品行为零影响**的设施。判据是：这个改动会不会让发布出去的东西变差？会，就是被禁止的让步；不会，它只是一个测试设施。

**事故一（2026-08-18）—— 规则诞生的原因**

D03 的规格为原子写选了**确定性的临时文件名**，动机纯粹是让 killer 好写。评审构造并发后，目标文件得到 `BBBBAAAA`——既不是任一写者的完整内容，也不是旧内容：两个 `File::create` 可以同时操作同一个 inode、互相截断交错写入，再由其中一个 rename 到目标。**为了测试方便而选了一个并发不安全的生产方案。**

**事故二（同日）—— 规则被用错**

同一份规格的下一轮，作者援引这条规则**拒绝加测试钩子**，理由是「测试不该塑造产品」。这是错的：`#[cfg(not(test))]` 下的 `#[inline(always)]` 空函数不产生任何指令、不改变任何行为，它不是产品让步。结果是那一轮的四条并发 killer 全部依赖调度巧合，**又花掉一整轮评审**。

作者自己的定性值得原样保留：

> 混淆这两者，让我用一条正确的原则为一个错误的结论辩护。

**为什么它有害**

一条正确的原则被用在错误的场景，比没有原则更危险——**它自带正当理由，所以不会被质疑**。规则写下来的时候必须同时写清它的边界，否则它会长出自己的适用面。

## R8 — 测试一个 helper，不等于测试这个 helper 被调用了

**规则**

当一条不变式的正确性依赖「某个生产路径确实调用了某个 helper」，测试必须**变异生产调用点**，而不是只变异 helper 内部。

写不出这种 mutant 时，把该调用点登记进验证缺口并给出可执行的人工检查点——**但不得再声称这条不变式已由自动化测试证明**。

**事故（2026-08-18，三个切片各一次）**

- D02：删掉生产代码里的预算检查、改回固定超时，对应测试**仍绿**；把受超时包裹的解码改成直接 await，对应测试**仍绿**。实现者可以把 helper 完整写出来并测好，却在真正的执行函数里漏接或绕过它们，而全套 49 条测试通过。
- D02（前一轮）：一条回归测试用「已关闭的端口」做 fixture，但规格自己规定这种情况返回成功，于是把错误处理改回原样**也不会红**——一个永远不会红的测试。
- D03：原子写的测试只验证了 helper 本身，**证明不了列出的 9 个生产写入点真的改用了它**；任一调用点改回旧写法，测试照样绿。

**为什么它有害**

这类测试给出的是最有欺骗性的一种绿：helper 的逻辑确实被证明了，覆盖率也真实存在，**唯一没被证明的恰恰是「它有没有接上」**。而漏接是实现阶段最常见的失误之一，尤其在重构或 rebase 之后。

D03 的修法给出了一个更强的方向：如果能让缺陷在**类型上不可表达**（例如去掉可失败的返回类型，使调用点根本没有可绕过的分支），那就不需要这个 mutant——**结构性保证优于测试保证**。

## R9 — 断言必须被证明是承重的

**规则**

每一条声称「独立可杀」的断言，都必须有一个**只让它单独失败**的用例；并且至少实跑一次「**移除该断言 ⇒ 该用例转 GREEN**」。

**多项同时失败的 fixture，不能作为任何单条断言的承重证据。**

不打算为某条断言提供单塌用例时，就不要声称它独立可杀——把它明确写成冗余，并把缺口登记进验收记录。

**事故（2026-08-18）**

D01 为了锁住一个已被实证存在的漏洞（命令 panic 而测试仍以 `EXIT=0` 通过），新增了一条 `child_ok` 断言和一个 panic 用例。评审实跑后发现：该用例同时让**返回值断言**与**终态断言**一起失败，于是**删掉 `child_ok` 断言，用例仍然 RED**。也就是说，实现者可以遗漏或写错 `child_ok`，而所有已声明用例仍保持预期颜色——那条断言写在那里，但没有任何东西证明它在起作用。

修法是把 panic 推迟到命令**完全跑完之后**（终态与返回值都已就绪），使四项里只剩 `child_ok` 会塌，然后实跑对照：

```
WITH    child_ok assertion   ⇒ RED
WITHOUT child_ok assertion   ⇒ GREEN
```

起草者自己的诊断是这条规则最好的表述：

> 一个多项同时失败的 fixture，**分不清「四道断言」和「三道断言 + 一句注释」**。

**与其他规则的关系**

这是同一族缺陷的第五个切面，全部在同一天出现：

| 环节 | 形态 |
|---|---|
| 输入 | fixture 静默退化（R6） |
| 过程 | 实跑的与落盘的分岔（R6 推广） |
| 结论 | 自我限定没扫全文 |
| 判定 | 判据写成「变体是否如其本性表现」而非「测试是否通过」 |
| 断言 | 断言存在，但没人证明它承重（本条） |

共同点：**每一环单独看都是对的，错的是环与环之间的连接**；而且没有一种会以「跑出错误结果」的形式暴露——它们全都表现为绿灯。
