# ApiSolo — 仓库硬规则

> **编号约定**：本文件的规则一律用 `P<n>` 前缀。**不要用 `R<n>`** —— 那是各切片 ACCEPTANCE 里的**评审轮次**编号（R1、R2……）。两套编号写进不同文档后，读者无法从字面区分「规则 R4」和「第 4 轮评审」。这条冲突是 D01 起草者在 2026-08-18 发现并上报的。

本文件**只收录在本仓库真实发生过、并造成了返工或证据失效的**违规。通用工程纪律不写在这里，它们在全局记忆里。

每条规则都要带上它诞生的那次事故——没有事故的规则会被当成教条而被忽略。

---

## P1 — 评审在飞行途中，被评审的产物一个字都不能改

**规则**

1. 任何产物（spec、实现、文档）交付一版后进入**只读**，由 owner 固化成一个 commit 作为 freeze 锚点。
2. 独立评审开始后到结论回来之前，该产物不得修改。作者发现自己写错了，**先报 owner**，由 owner 决定中止评审重跑、还是记进 disposition 下一轮一起改。
3. 跨切片的协调结论**先报 owner 裁定，再落盘**。跨切片措辞是两份 spec 共同的契约，任一方单方面改写会让另一方的评审结论一并失效。
4. 只有 owner 下发修订指令时，才是作者的写入窗口。

**事故（2026-08-18）**

同一天连续发生两次。owner 于 12:02:04 将 D01 的 rev3 交付独立评审；起草者在 12:08:44 与 12:09:15 分别修改了 `PRODUCT.md` 与 `TECH.md`。D03 同样：评审 12:09:41 启动，起草者随后做了三处改动。两次改动的**内容本身都是对的**，都是与另一个切片协调后的正确结论——问题纯粹在时序。

**为什么它有害**

评审结论会指向一个磁盘上已不存在的版本，于是无法判断「评审没报这个问题」到底是因为不存在，还是因为它读的是旧文本。这直接摧毁了 owner-pipeline 的核心资产：三条证据流（实现者自检 / owner 亲跑 gate / 评审结论）互相独立且互不顶替。一条证据的时间锚点一旦模糊，它就不再是证据。

**责任归属**：这两次的根因是 owner 派单时没有交代规约，不是起草者的过失。规则写在这里是为了下次不再依赖某个人记得。

## P2 — 「我验证过」必须写明验证的是什么

**规则**

声称实跑验证时，必须写明跑的是**哪个东西**。特别是：验证一个外部工具的行为，必须跑那个工具本身，而不是跑自己对它的实现。

**事故（2026-08-18）**

D06 的 spec 声称已实跑验证 `--data-urlencode` 的编码行为，写的是空格编码成 `%20`。owner 在本机跑真实 `curl 8.7.1`，得到的是 `q=a+b%26c`——空格是 `+`。起草者跑的是自己的实现，不是 curl。若未被抓到，这个错误会连同一条断言一起被冻结进回归测试，从此以「已验证」的姿态长期存在。

同一天另一次：`docs/review/REVIEW-2026-08-18.md` §28 的对抗验证记录称某个 JSON 输入脱敏后是安全的，实跑为非法 JSON。**一份写着「已对抗验证」的文档，其个别条目仍然可能是错的。**

## P3 — 变异检查列必须是可编译的单行改动，且必须真的能杀死测试

**规则**

每条不变式的 mutation killer 必须是一个**能编译的单行 patch**，并写明改动后**哪一条断言会红**。写不出来就说明这条测试是同义反复，重新设计测试；两条不变式确实共用一个 killer 时如实标注，不许编造第二个。

**事故（2026-08-18）**

D01 与 D02 的规格都声称「每条不变式都有可执行的变异 gate」，评审实跑后查出多条 **survivor**：删掉正则的 `lastIndex = 0` 复位后，幂等测试仍然全绿；另有多条 killer 根本编译不过（引用了尚未定义的变量、不符合目标函数签名）。

D01 深挖后发现根因比「漏了个复位」更根本：`exec` 循环命中即 `return` 会留下非零 `lastIndex`，于是幂等断言的结果**取决于该测试在文件中的位置**。修法不是补复位，而是把正则改成函数内构造，从结构上消除共享状态。

**为什么它有害**

放行的话，我们会拿着一张「每条不变式都有测试保护」的表，而表里有几行是假的。一张不可信的验收表比没有表更危险。

## P4 — 不得把其他 agent 的陈述当作事实写进持久产物

**规则**

需要引用另一个 agent 的产出时，二选一：**亲自确认它存在且内容如此**，或者写成转述并标明未验证来源（「据 D03 称」）。不许用陈述句把听来的东西写成既成事实。

**事故（2026-08-18）**

D01 的 spec 写下「`specs/D03-persistence/TECH.md` §2.2 记录了本切片的锁契约」。写下的那一刻，`specs/D03-persistence/` 在该工作树里**根本不存在**——对方在独立 worktree 里工作。一条 `ls specs/` 即可发现。

**为什么它有害**

起草者自己的定性最准确：两个切片**互相把对方的口头陈述当作可引用的事实写进了各自的 spec，于是两份文档在没有任何一方验证的情况下产生了耦合**。这比单纯的悬空引用更糟——悬空路径至少会在有人点开时暴露，而未经验证的相互引用会一直读起来像是已经对齐过了。

这也是 P1 第 3 条（跨切片结论先经 owner）的真正价值所在：只有 owner 同时看得到两份产物的真实状态。

**最难自觉执行的形态：未验证的推断伪装成因果解释**

同一位起草者，在**专门记录这条规则的那段事故说明里**，又写了一句未验证的断言——「（对方在独立 worktree 里）」。那是它从「`ls specs/` 看不到那个目录」推出的合理猜测，后来被 owner 独立佐证为真，但写下的当时并未核实。

它自己的定性是这条规则最有用的补充：

> 那句话在我写的时候感觉不像一个断言，感觉像在**解释一个显而易见的原因**。未验证的推断伪装成因果解释的时候最难被自己抓住——比伪装成引用还难。

所以 R4 的适用面不止「引用对方的产出」。**任何写进持久产物的因果解释，只要它的依据是推断而非核实，就要按转述标注。** 引用至少长得像引用，会提醒你去查；因果解释读起来像理解，不像主张。

## P5 — 跨文档引用只能引用行为，不得引用任何外部标识符

**规则**

判据不是「它是不是号码」，而是**「它的身份是否由另一个文档单方面决定、且可能在你不知情时改变」**。章节号、条目 ID、文件路径，全部在内。

- **跨切片引用**（一份 spec 指向另一份 spec）：只描述行为，不带任何标识符。
- **指向 `specs/BACKLOG.md` 的裁定台账**（A1–A10）：**允许**。该表由 owner 维护，只追加不重编号，owner 为其稳定性负责——这正是它存在的意义。
- **指向切片内的局部枚举**（如某切片的交接项 `C1`）：不允许，那些是会随 scope 调整重排的临时列表。
- **同一份文档内部的自引用**：不受限。

**事故（2026-08-18）**

D01 的 spec 在四处引用了 D03 的章节号与条目 ID。而 D01 自己的不变式编号在三轮修订里走过 27 → 34 → 39，D03 当时尚未定稿——任何这类指针都必然烂掉，区别只是烂在评审时还是半年后。`specs/BACKLOG.md` 的 `REVIEW #n` 编号也已经 churn 过一次（整体偏移 +2）。

初版规则只写了「不得引用章节号」，范围太窄，是起草者主动扫描作用面时发现还有条目 ID 和文件路径两种同类变体。

## P6 — 会静默退化的 fixture，测试必须先自检 fixture 再断言行为

**规则**

当测试的输入本身可能在**写入或复制过程中被解释掉**（转义序列、不可见字符、行尾、编码），测试要先断言「我的输入确实还是我想要的那个输入」，再断言行为。

不要靠「下次写的时候小心点」。如果退化来自工具链而非笔误，小心是无效的对策——**换掉依赖**：改用运行时构造（例如用 `String.fromCharCode(92)` 拼出反斜杠）而不是手写字面量，并在文档里改用一个不会被任何环节解释的替身符号。

**事故（2026-08-18）**

D01 的规格声称对比「普通键 `password`」与「转义键 `\u0070assword`」，但文件里两边**实际都是普通的 `password``**——反斜杠在写入时被吃掉了。后果：照这份 fixture 写出的测试，把 `isSensitiveKey(decodeJsonKey(raw))` 换成 `isSensitiveKey(raw)` 仍然全绿，也就是那条不变式**什么都没有证明**。

起草者修复时反斜杠**又被吃了一次**，`String.raw` 也没救回来，最后是 `od -c` 做字节级核对才发现。进一步探针显示这是系统性的：该写入链路会把合法转义解释掉，而非法转义反而原样保留。

**为什么它有害**

这是 P3（killer 必须真能杀死测试）的一个更隐蔽的变体。killer 杀不掉至少还能在应用 mutant 时被发现；**fixture 退化则让测试一路绿着通过，看起来是最健康的状态**。一个断言了错误输入的测试，比没有这条测试更坏——它占着「这条不变式已被覆盖」的位置。

## P7 — 变异检查用来验证设计，不用来塑造设计；但别把这条规则用错地方

**规则**

写不出 killer 时，正确的反应是**重新设计测试**，不是**弱化产品**。

**但这条规则只禁止「让产品变差」。** 它不禁止为了可测性添加**对产品行为零影响**的设施。判据是：这个改动会不会让发布出去的东西变差？会，就是被禁止的让步；不会，它只是一个测试设施。

**事故一（2026-08-18）—— 规则诞生的原因**

D03 的规格为原子写选了**确定性的临时文件名**，动机纯粹是让 killer 好写。评审构造并发后，目标文件得到 `BBBBAAAA`——既不是任一写者的完整内容，也不是旧内容：两个 `File::create` 可以同时操作同一个 inode、互相截断交错写入，再由其中一个 rename 到目标。**为了测试方便而选了一个并发不安全的生产方案。**

**事故二（同日）—— 规则被用错**

同一份规格的下一轮，作者援引这条规则**拒绝加测试钩子**，理由是「测试不该塑造产品」。这是错的：`#[cfg(not(test))]` 下的 `#[inline(always)]` 空函数不产生任何指令、不改变任何行为，它不是产品让步。结果是那一轮的四条并发 killer 全部依赖调度巧合，**又花掉一整轮评审**。

作者自己的定性值得原样保留：

> 混淆这两者，让我用一条正确的原则为一个错误的结论辩护。

**为什么它有害**

一条正确的原则被用在错误的场景，比没有原则更危险——**它自带正当理由，所以不会被质疑**。规则写下来的时候必须同时写清它的边界，否则它会长出自己的适用面。

## P8 — 测试一个 helper，不等于测试这个 helper 被调用了

**规则**

当一条不变式的正确性依赖「某个生产路径确实调用了某个 helper」，测试必须**变异生产调用点**，而不是只变异 helper 内部。

写不出这种 mutant 时，把该调用点登记进验证缺口并给出可执行的人工检查点——**但不得再声称这条不变式已由自动化测试证明**。

**事故（2026-08-18，三个切片各一次）**

- D02：删掉生产代码里的预算检查、改回固定超时，对应测试**仍绿**；把受超时包裹的解码改成直接 await，对应测试**仍绿**。实现者可以把 helper 完整写出来并测好，却在真正的执行函数里漏接或绕过它们，而全套 49 条测试通过。
- D02（前一轮）：一条回归测试用「已关闭的端口」做 fixture，但规格自己规定这种情况返回成功，于是把错误处理改回原样**也不会红**——一个永远不会红的测试。
- D03：原子写的测试只验证了 helper 本身，**证明不了列出的 9 个生产写入点真的改用了它**；任一调用点改回旧写法，测试照样绿。

**为什么它有害**

这类测试给出的是最有欺骗性的一种绿：helper 的逻辑确实被证明了，覆盖率也真实存在，**唯一没被证明的恰恰是「它有没有接上」**。而漏接是实现阶段最常见的失误之一，尤其在重构或 rebase 之后。

D03 的修法给出了一个更强的方向：如果能让缺陷在**类型上不可表达**（例如去掉可失败的返回类型，使调用点根本没有可绕过的分支），那就不需要这个 mutant——**结构性保证优于测试保证**。

## P9 — 断言必须被证明是承重的

**规则**

每一条声称「独立可杀」的断言，都必须有一个**只让它单独失败**的用例；并且至少实跑一次「**移除该断言 ⇒ 该用例转 GREEN**」。

**多项同时失败的 fixture，不能作为任何单条断言的承重证据。**

不打算为某条断言提供单塌用例时，就不要声称它独立可杀——把它明确写成冗余，并把缺口登记进验收记录。

**事故（2026-08-18）**

D01 为了锁住一个已被实证存在的漏洞（命令 panic 而测试仍以 `EXIT=0` 通过），新增了一条 `child_ok` 断言和一个 panic 用例。评审实跑后发现：该用例同时让**返回值断言**与**终态断言**一起失败，于是**删掉 `child_ok` 断言，用例仍然 RED**。也就是说，实现者可以遗漏或写错 `child_ok`，而所有已声明用例仍保持预期颜色——那条断言写在那里，但没有任何东西证明它在起作用。

修法是把 panic 推迟到命令**完全跑完之后**（终态与返回值都已就绪），使四项里只剩 `child_ok` 会塌，然后实跑对照：

```
WITH    child_ok assertion   ⇒ RED
WITHOUT child_ok assertion   ⇒ GREEN
```

起草者自己的诊断是这条规则最好的表述：

> 一个多项同时失败的 fixture，**分不清「四道断言」和「三道断言 + 一句注释」**。

**与其他规则的关系**

这是同一族缺陷的第五个切面，全部在同一天出现：

| 环节 | 形态 |
|---|---|
| 输入 | fixture 静默退化（P6） |
| 过程 | 实跑的与落盘的分岔（P6 推广） |
| 结论 | 自我限定没扫全文 |
| 判定 | 判据写成「变体是否如其本性表现」而非「测试是否通过」 |
| 断言 | 断言存在，但没人证明它承重（本条） |

共同点：**每一环单独看都是对的，错的是环与环之间的连接**；而且没有一种会以「跑出错误结果」的形式暴露——它们全都表现为绿灯。

## P10 — 度量与结论分开写

**规则**

报告验证结果时，**度量**与**结论**必须是两句话，并且结论必须自带它的适用范围。

- 度量：「58 个变异全部变红。」
- 结论：「因此 helper 内部的逻辑已被覆盖。**变异全部打在 helper 内部，调用点这一层未被触及。**」

不写第二句，一个真实的数字就会替一个它撑不起的主张背书。**读报告的人（包括 owner）会按结论行动，而不是按度量行动。**

**事故（2026-08-18）**

D01 的实现者报告「58 个变异全红、0 存活、0 无效」。每一个数字都是真的：变异真的打上去了、目标测试真的执行了非零用例、真的全红。

但那些变异全部打在脱敏 helper **内部**。独立评审绕过 `sanitizeHistoryEntry` 的**五个生产调用点**后，**完整 183 个测试仍然全绿**——也就是说，将来任何一次重构漏接其中任一条，凭据就会明文进入历史，而整套 gate 不会报错。

实现者自己的定性是这条规则的最好表述：

> 这个数字真实，但它证明的东西比它听起来的小得多。

以及后来那句更具操作性的：

> 「58 个变异全红」是度量，「实现已被充分验证」是结论。我把两者混成一句话，等于用一个真实的数字替一个更大的主张背书。

**为什么它对 owner 同样重要**

owner 亲跑的 gate（vitest 183 全绿、cargo 80 全绿）**同样看不见这个缺陷**——gate 只能证明"现有测试都通过"，证明不了"现有测试覆盖了该覆盖的东西"。当时唯一指向"已充分验证"的证据，就是那句混写的报告。**owner 差一点据此合并。**

这也是三条证据流互不顶替的具体含义：实现者自检与 owner 跑 gate 都以「绿」为形式，**只有独立评审会去问「有什么是绿了也不算数的」**。

**与 P8 的关系**

P8 讲的是**怎么测**（要变异调用点，不只是 helper）。P10 讲的是**怎么报**（真实的度量不等于它暗示的结论）。同一个缺陷可以被 P8 挡在写测试的时候，也可以被 P10 挡在读报告的时候——两道都要。

## P11 — 跨边界的字段，去读产出它的那一侧

**规则**

任何跨越语言/进程边界的字段（Rust ↔ TS、IPC、序列化），判断它的形状时**读产出它的那个结构体定义，不读消费它的那个类型声明**。

fixture 要用**真实序列化后的形状**构造，不要用本侧类型声明推出来的形状。

**事故（2026-08-18，已发布到 main）**

Postman 导出用 `item.fileContent !== undefined` 判断上传是否内联。而 Rust 每次从磁盘读取保存的请求都会把 `file_content` 置 `None`（`lib.rs:1453`），且该字段**没有 `skip_serializing_if`**，于是它以 JSON **`null`** 抵达前端。`null !== undefined` 恒为真，谓词**永远成立**。

后果不只是一条多余的告警：导出的 collection **对每个文件行写入一条虚假说明**（「内容存在 ApiSolo 里、无法导出」——内容从来就不在那里），**并且整个丢掉 `src`**，文件名在 Postman 里不可恢复。

**四轮规格评审 + 一轮独立代码复审全部漏掉**，因为所有 fixture 用的是 `"aGVsbG8="` / `""` / `undefined`，**`null` 一次都没用过**。

**根因比「fixture 写错了」更靠前**

修复者的定性比第一版规则准确，原样保留：

> 我的规格 §1.4 断言「`filePath` 恒为空」，依据是读了 `BodyEditor.vue` 与 `projects.ts`——我追的是**前端的写入路径**，从没问过 Rust 在**读取时**交回来什么。**fixture 跟着声明走，是因为分析跟着声明走。**
>
> 「用真实序列化 fixture」这条规则能抓到它；而「跨边界的字段要读产出方的结构体、而不是消费方的类型」这条能**更早**抓到它。

前端的类型声明 `fileContent?: string` 本身就是错的——它描述的是前端**自己构造**该对象时的形状，不是**线上真实**的形状。于是每一个作者（规格、实现、评审）都照着它写 fixture，而两侧各自都自洽，**它们之间的契约没有任何测试覆盖**。

**与 P6 的关系**

P6 讲 fixture 会在写入过程中**静默退化**。P11 讲 fixture **从一开始就没模拟真实契约**。前者是变质，后者是取材错了——而 P11 的形态更隐蔽，因为 fixture 与它所依据的类型声明**完全一致**，从本侧看不出任何问题。

## P12 — 度量装置必须 fail-closed：「没跑」不得被读成「跑了且没事」

**规则**

任何自动判定的度量脚本（变异台账、检查工具、CI 判据），**判据必须正向匹配「确实执行了」的证据**，而不是反向匹配「出现了失败标志」。

找不到执行证据时的默认结论**必须是 `INCONCLUSIVE`，绝不能是良性结论**。

再加一层交叉校验：解析出的失败计数与失败条目数量不一致时，同样记 `INCONCLUSIVE`。

**事故（2026-08-18）**

D02 的变异台账产出 **57 行「SURVIVED」（变异存活）**。全部是假的。

根因：脚本用绝对路径调用 `cargo`，但 `rustc` 仍从 `PATH` 解析到 Homebrew 的 1.87，于是**每一次编译都直接失败**，输出 `error: rustc 1.87.0 is not supported`。而脚本的编译失败判据只匹配 `error[E` 与 `error: could not compile`，两个都没命中。没有 `FAILED` 行 → 判成「测试通过 → 变异存活」。

**一次都没真正跑过，而台账写着 57 个结论。**

作者自己的定性是这条规则的最好表述：

> 「57 个 mutant 全部存活」是一个真实的度量，**它度量的是一个坏掉的脚本**。

修法是把判据反过来：必须 positively 找到 `test result: … N passed; M failed`；找不到、或 `N+M == 0`，一律 `INCONCLUSIVE`。并且**先用一个已知必红的变异验证 harness 本身**，再开始跑真实台账。

**与 P10 的区别**

P10 是**报告**层面：度量真实，但结论超出了它能支撑的范围。P12 是**判据**层面：装置把「缺少证据」直接读成了「证据表明无事」。

P12 更危险，因为 P10 至少有一个真实的测量作底；P12 连测量都没发生，而输出看起来完全一样。

**已知诱因**：项目记忆早已记录「Homebrew 的 rustc 会遮蔽 rustup，必须走 `npm run test:rust`」。这次仍然中招，因为作者写的是**自己的脚本**而不是那条 npm 命令——**已知陷阱不会因为被记录过就自动避开，它只在你走既定路径时才被绕过。**

## P13 — greenfield 切片在规格阶段的 VERIFIED 必然为 0

**规则**：如果一条不变式对应的生产代码**尚不存在**，那么它的变异 killer 在规格阶段**不可能**是 VERIFIED。任何非零的 VERIFIED 计数，都意味着有个模型在冒充生产代码。规格阶段能诚实声称的最强状态是 **DESIGNED**。

**事故**：D05 的三态台账，VERIFIED 一栏被修正了三次，一次比一次小：

```
rev3 之前   51 条「独立 killer」   ← 撤回：那是关于文档的陈述，不是关于覆盖的陈述
rev4         6                    ← 撤回：非单塌、半验证被算进来了
rev5         2                    ← 撤回：两条都跑在临时模型上
rev6         0                    ← 唯一可能的诚实答案
```

第三次修正是终局性的：`§11` 实际跑的是 `/tmp/urlbar-rev3.mjs` 里**重新实现的**协调器——生产树里 `src/utils/url-params.ts` 不存在；`§12(a)` 那个"变异"是 `const WITH_REVISION = process.env.MUT !== "1"`，它切换的是**临时测试自己**的 watch 数组，而 `UrlBar.vue` 里那个 watcher 也还不存在。

**每一个非零数字，都是「模型顶替了生产」这一件事的不同伪装。**

**为什么值得单列成规则**：这四轮里没有一轮是白费的——每一轮都真的抓到了错误分类。但**终值从第一轮起就是可推导的**：greenfield ⇒ 生产代码不存在 ⇒ 无处可打补丁 ⇒ VERIFIED 必为 0。有了这条规则，那三轮不必发生。

**这不是「模型验证没有价值」**。模型能回答「这个测试形状抓不抓得住这个缺陷形状」。它回答不了两件事，而这两件事都有实测证据：

- **模型低估真实耦合，且方向单向**（D02 实测，落到真实 `lib.rs` 后）：`K7` 模型杀 1 条 / 真实杀 **14** 条；`KDEFAULT_1252` 模型 3 / 真实 **7**。没有一条在真实代码上杀得更少。
- **模型可以双向出错**（同一批实测）：`KFAIR`/`KFIRST` 在模型上杀伤集合**完全相同**，真实代码上**可区分**——据此写下的「§37 与 §38 并不正交」结论必须撤回。

**执行**：规格阶段的台账只允许两栏——`DESIGNED`（补丁已写、位置已定、有对应断言）与 `INCONCLUSIVE`。`VERIFIED` 一栏留空，标明「转正条件：实现落盘后对真实模块应用补丁，按同一判据重测」。

**阶梯**（D04 冻结时自评发现的，它的位置比 D02 更弱）：

| 强度 | 含义 |
|---|---|
| 真实代码上跑过并记录**完整杀伤集合** | 最强 |
| 真实代码上跑过、只记「红了」 | 缺连带杀伤信息 |
| 模型上跑过 | 系统性低估真实耦合，可双向出错 |
| **一次都没跑过**（读着生产代码设计出来） | 只证明可编译、位置对、有断言对应 |

D04 的 35 条 killer 属最后一档，且**没有任何一行**做过 P9 的「删掉断言 ⇒ 转绿」对照。它在冻结时把这件事写进了规格，而不是等评审来问。

**病态的不是「建模型」这个动作**

D02 建模是对的——它当时**有可跑的对象**。病态的是**让计数驱动方法选择**：先有「VERIFIED 不能是 0」这个期望，再倒推出一个能产生非零的装置。**同一个动作，前者是工具，后者是替身。**

所以本条的执行面不是「禁止建模」，而是：**当你发现自己在为了让某个计数非零而设计装置时，先问那个计数在当前阶段是否本来就该是 0。**

**为什么四轮里没人问出这个问题**：51→6→2→0，每一次降级都是正确的，每一次都真的抓到了错误分类。**正因为数字在动，它看起来就像在收敛**——而收敛感掩盖了「这个量在 greenfield 阶段本来就是病态的」。一个持续变小的错误答案，比一个不动的错误答案更难被质疑。

## P14 — 空补丁的变异必须报错，不得记成 `SURVIVED`

**规则**：变异 harness 在运行一个 mutant 之前，必须确认它的补丁**产生了非空 diff**。补丁为空 ⇒ 立即报错并中止该条，**绝不允许进入"跑了、没红、记 SURVIVED"这条路径**。

**事故**：D02 的台账记录：

```
| WIRE_PROBE_CONST 把常量而非 probe_budget(...) 传给探测 | 存活 | 预期，冻结前已登记（缺口 #5）|
```

独立评审逐行追参数流后发现，生产代码是这样的：

```rust
// 调用点算了预算并传进去
measure_connection_timings(&url, probe_budget(overall_deadline, Instant::now())).await

// 收下了 budget，但只用作外层 timeout；没有传进 blocking 闭包
tokio::task::spawn_blocking(move || probe_connection(host, port))

// 里面固定用常量
connect_first_reachable(&addrs, CONNECTION_PROBE_MAX)
```

**预算在三行之间确定性丢失。** 把「传常量而非 `probe_budget`」这个变异，打进一份**本来就在传常量**的代码里——**补丁是空的**。

于是这个 mutant「存活」，被记成「预期内的覆盖缺口」，而真相是：**生产代码已经具有该 mutant 的行为，那是一个已发布的 bug**。后果按 §38/§41：总预算只剩 2 秒、解析到两个地址时，第一个地址仍按常量拿到 2.5 秒份额，外层 timeout 先到，**第二个地址永远没有机会被尝试**——而 §38 的全部意义就是"每个地址都要有份"。

**为什么必须单列成规则**

变异台账的价值主张是「**存活 ⇒ 那段代码没被测到**」。但存活有三种成因，此前只枚举了两种：

| 成因 | 含义 | 处置 |
|---|---|---|
| 用例覆盖不到那条路径 | 真正的覆盖缺口 | 登记缺口 |
| 该行为本就不可用廉价手段测出 | 已知限制 | 登记并写检查点 |
| **补丁是空操作** | **生产代码已经是错的** | **修 bug** |

**光看 `SURVIVED` 这个信号，三者无法区分**——必须去看 diff。而第三种恰恰会伪装成第一种：一个"预期存活"的分类，读起来像是尽职的风险登记，实际上把一个 bug 归了档。

**与 P12 的关系**：P12 是装置**没跑**却报了结论；P14 是装置**跑了**、结论也真实（确实没红），但**输入本身是空的**，于是那个真实的结论回答的是另一个问题。两者都是"度量装置在骗你"，但 P12 骗在执行，P14 骗在输入。

**执行**：mutant 应用后立刻确认补丁非空、锚点唯一、写回后文件确实变了；任一不满足则以醒目错误中止。并且——**对每一条历史上记为"预期存活"的条目，回头重查它的补丁是否真的改变了行为**。这类条目读起来最无害，因此最不会被复查。

### 更正：上面那道机械守卫，挡不住产生本规则的这次事故

`WIRE_PROBE_CONST` 的补丁**文本上是非空的**——`probe_budget(...)` → `CONNECTION_PROBE_MAX`，两个不同 token，diff 有内容。它是**语义**空操作。

而且还有第二层巧合，是实现者复查时发现的：**全部用例的总预算都是 30 秒，`min(5s, 30s)` 恰好等于那个常量**，所以连外层 timeout 的行为都没有差别。两条独立的路径同时使补丁不可观察。

所以本规则分两层，**只做第一层会制造虚假的安全感**：

| 层 | 抓什么 | 手段 |
|---|---|---|
| 文本空操作 | 补丁没落地、锚点没匹配、写回失败 | **机械守卫，必须有** |
| **语义空操作** | 补丁落地了，但生产代码本就是这个行为 | **只能靠人读补丁真正改变了什么** |

实现者的原话：

> 机械守卫我已加进 harness，但它**只能挡住文本空操作**；语义空操作仍然需要有人去读补丁真正改变了什么。这一点值得写进规则，否则会给人一种「加了守卫就安全了」的错觉。

**推论**：`SURVIVED` 这个结论永远需要一次人工问答——**「如果这个补丁生效了，谁会看见？」** 答不上来的，不是缺口，是待查。

**而这句问答本身还需要再钉一层**，因为它单独用是不够的。实现者的复盘：

> `WIRE_PROBE_CONST` 这条，我当时**答得上来**——「预算变小，第二个地址会被跳过」——但那个答案描述的是**规格里的代码**，不是**磁盘上的代码**。

所以补一条硬形式：**答案必须落在具体行号上。** 不是「预算会变小」，而是「`:276` 这一行会从 `remaining` 变成常量」。

> 我如果当时被迫写出那句话，就会立刻发现它本来就是常量。

这是 **P11**（跨边界的字段去读产出它的那一侧）在变异台账上的同一条纪律：**描述的是哪一份代码，必须由行号来指认，不能由记忆来指认。**

### 同一条纪律在计数上的形态：基线数字必须带 commit

同一轮里发生过一次两人都没错、结论却错了的事故。

owner 在派单时写「main 当前：vitest 20 files / **276** passed」，实现者据此在报告里写「276，与基线一致」。后来 owner 实测 main 为 **277**，判定实现者误报，并在 ACCEPTANCE 里记了一段批评。实际查证：

| 数字 | 对应 commit |
|---|---|
| 276 | `c9221d3` —— 实现者的分支基点，**也是 owner 派单当时的 main** |
| 277 | `c7e620e` —— 后来合入 PR #15/#16/#17 之后 |

差的那一条是 **PR #15 为已发布缺陷加的回归测试**。**两个数字都是真值，两句话在各自的时刻都成立**，中间隔着三个 PR。

**错在没有把数字钉到 commit 上。** 实现者的定性：

> 「main 是 277」和「`c7e620e` 是 277」看起来一样，**前者会随时间静默变假。**

**执行**：任何写进报告、台账或 ACCEPTANCE 的测试计数、基线、门禁结果，一律写成 `<数字> @ <commit>`。裸的「与基线一致」是无效表述——**说这句话的人必须能指出他在跟哪个 commit 比**。

**附带的一条**：owner 那次的错误判定，是在自己已经写下 P10、并用 P10 纠过别人之后犯的；纠正之后的第一版更正（「你的数字对你的树准确」）**仍然把运气说成了方法**，直到实现者查出时间轴才化开。**一个恰好成立的结论和一个被证明成立的结论，长得一样**——这与 P9 是同一件事，只是从断言换到了结论。

### 同族的第三种：补丁改变了语义，但改变的部分不可观察

D04 R2 实测：为「等锁预算」与「取消通道」两半修法各设计的 killer，三轮实跑都不杀（`WRITER_RELEASED=true`），只有整条取消路径删掉才可观察。

根因不是探针不灵敏，**是设计本身**：规格早已规定「`watch::Sender` 被 drop 也按已取消处理」，于是显式 `send(true)` 是**冗余语句**；而取消路径在时，等锁根本长不到需要预算兜底。

处置不是硬凑 killer，而是老实记「承重部分有 killer，冗余/纵深部分保留但各自无独立 killer」，**并写明保留理由**。

**由此引出一条给实现的硬要求**：一个**既无测试覆盖、删掉又不改变任何可观察行为**的部件，在下一个人眼里与死代码无法区分。**保留理由必须写进代码注释，不能只写在规格里**——重构的人读的是代码。

### 清单要回填计数，不要打勾

D04 的收尾清单当场抓到它自己日志里的错：写「假绿不可达 5 处」，实跑是 **7 处**——因为记录写在最后两处编辑之前。

> **勾可以在动作之前打，数字不行。**

打勾式清单是自证的。凡是要求「做过某个动作」的流程清单，一律改为**回填该动作产出的真实计数或名单**。对变异台账的具体形态：每条声称"单塌"的，收尾时回填**它实际杀死的用例名单**——名单出现第二个名字就是没单塌，名单为空就是没跑。
